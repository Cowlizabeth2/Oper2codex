# Расхождение SQLite и демонстрационного интерфейса — 0.3.2

**Пользовательская база пока не предоставлена. Её записи и результат обновления ещё не проверены; задачу для этой базы нельзя считать завершённой.** Ниже — установленный механизм, реализация безопасного преобразования и проверка исторической базы, созданной старым кодом. Это не подмена проверки пользовательского файла.

## Причина, воспроизведённая на старом приложении

SQL-схема `user_version=1` и формат `segments` существуют с версии 0.1. В коммите `4674b65a4614d623350cbca109a92c32e0e5f736`, как и позднее, `Controller.insertField` сохраняет весь выделенный фрагмент в `field.default`. Выделение самой подписи `Время: ` делает её содержимым поля. Сотрудник может оставить подпись и дописать время; в SQLite получится значение `Время: 14:35`.

`Controller.get_state → inline_tokens` не меняет вид сегмента: `kind=field` становится `token=field`. Поэтому приложение 0.3.1 правильно рисует инпут для того, что в базе объявлено полем, включая записанную внутри подпись. Исправление внешнего вида не преобразует данные. Демонстрация 0.3.1 сразу содержала отдельный `kind=text`, и старое содержимое не проверяла — это был пробел в предыдущей проверке.

Целевая структура внутри TextTemplateBlock: постоянный сегмент `{"kind":"text","text":"Время: "}` и прежний `field` с тем же UUID, значением `14:35`. Это не отдельный компонент StaticTextBlock и не CSS-маскировка. Обновляются фактические JSON-записи SQLite. `controller.py`, `domain.py`, `InlineMessage.qml` продолжают использовать прежнюю модель чтения/отображения.

## Безопасный порядок в приложении

В настройках доступно «Проверить структуру шаблонов…». Диагностика показывает UUID блока/поля, `kind`, предшествующий сегмент, `default`, фактическое сохранённое значение, наличие значения, фразы и неизвестные ключи значений. Читаются черновик, опубликованная конфигурация и все снимки происшествий, включая архив.

1. Выберите поле и вручную укажите точный постоянный префикс, включая пробелы. Программа не угадывает его по `label`, двоеточию или названию поля.
2. Откройте предпросмотр. Для каждой версии/карточки показаны default, value и phrases до/после. Можно открыть полное сообщение до/после. Отличия копируемого текста или применения фраз отмечены отдельно.
3. Отметьте нужные записи по отдельности: по умолчанию не выбрана ни одна, включая неоднозначные. Подтвердите просмотр и нажмите «Создать резервную копию и применить».
4. Под блокировкой записи повторно проверяется отпечаток всех конфигураций и происшествий. Если база изменилась, применяется отказ без перезаписи — нужен новый предпросмотр.
5. До первого UPDATE SQLite backup API создаёт полную согласованную копию `backups/before-template-migration-<uuid>.sqlite`. При невозможности создать копию изменения запрещены. Затем вся выбранная группа меняется одной транзакцией. Ошибка в середине откатывает все записи; копия остаётся.

Переносится только ровно указанный префикс и только один раз. Оставшаяся часть значения сохраняется посимвольно, без trim/нормализации. UUID, прочие параметры поля, порядок и количество фраз, связи блоков, ID/номера/статус событий, документы, другие поля и история не удаляются. У фразы с этим точным префиксом он выносится в постоянный текст; остальные фразы остаются целиком. Исходные необрезанные строки доступны в обязательной резервной копии. Предпросмотр явно показывает изменение строк и смысл применения фраз.

Если в старом событии хранится только `17:40`, эта строка остаётся `17:40`. Добавление постоянной подписи изменит результат копирования; запись отмечается предупреждением и требует явного выбора. Если default другой версии не начинается с префикса, перед полем уже есть такая подпись, структура неизвестна или обнаружены значения без известных UUID, преобразование соответствующей записи запрещается. Неизвестные соответствия не восстанавливаются догадками.

Записи без выбора не переписываются даже при совпадении UUID. Исходный черновик, опубликованная версия и существующие снимки выбираются отдельно. После применения очищается только история Undo/Redo конструктора в памяти, чтобы она не вернула старый JSON поверх подтверждённого исправления. Результат и путь копии записываются в журнал и `preferences.template_migration_runs`; значения сообщений в журнал не попадают. Откат базы выполняется обычным восстановлением выбранной резервной копии.

## Проверка обновления существующей базы

Фикстура `tests/fixtures/legacy-template-0.1.sql` получена **историческим кодом 0.1**, а не текущим конструктором. Генератор извлекает Python-модули из коммита `4674b65a4614d623350cbca109a92c32e0e5f736`, вызывает старые `insertField/saveTemplate/publish/create_event/setValue`, создаёт два происшествия, архивирует одно и сохраняет SQL-дамп SQLite. Происхождение, ID и SHA-256 дампа записаны в соседнем JSON. Данные полностью синтетические.

Тест загружает этот замороженный дамп через стандартный `sqlite3`, копирует старую SQLite-базу через backup API, затем открывает **копию** новым Store/Controller. Он сначала воспроизводит подпись внутри инпута, затем проходит предпросмотр и подтверждение, открывает то же старое событие и проверяет отдельный неизменяемый текст. Новый инцидент для доказательства не создаётся.

Девять тестов миграции проверяют: отсутствие тихого преобразования при старте; точность снимка резервной копии; UUID, связи, значения и фразы; перезапуск; отказ без подтверждения; сохранность неоднозначной невыбранной карточки; отказ при ошибке backup; полный rollback при позднем отказе UPDATE; устаревший предпросмотр; неизвестную структуру и неизвестные ключи значений; фактический GUI и полный SHA в настройках.

`tools/review_template_migration.py` дополнительно захватывает старую существующую карточку до/после в обеих темах и пишет отчёт. В отчёте намеренно стоит `user_database_verified: false`. Преобразуются по три явно выбранные записи для двух полей (черновик, опубликованная версия, первое старое событие); второе архивное событие остаётся без изменений. После этого проверяется повторное открытие обновлённого файла, неизменность полного сообщения и отсутствие новых происшествий.

## Идентификация сборки

Настройки показывают полный, выделяемый для копирования SHA. Windows-сборка требует 40-символьный SHA; `build.json` включается в EXE, smoke-отчёт возвращает SHA, а упаковщик сравнивает его с SHA запуска Actions. Короткое значение или `local` не принимаются за идентификатор опубликованной сборки.

## Что ещё необходимо для выполнения запроса

Нужна резервная копия реальной пользовательской `.sqlite`. Сначала — чтение и фиксация фактических структур/значений; затем — подтверждённый план для её неоднозначных записей, backup и проверка на отдельной копии. До этого ни происхождение именно пользовательского случая, ни результат его исправления не объявляются подтверждёнными.

Локальная проверка: **92 passed, 1 skipped** (только нативный Windows CF_HDROP), включая девять тестов обновления/миграции и пять проверок идентификатора сборки. [Машинный отчёт проверки исторического файла](template-migration-local-report.json): backup integrity OK, ID старого события сохранён, новых событий 0, сообщение совпало посимвольно, повторное открытие обновлённой SQLite успешно.
